# Live Deployment Orchestration & Sign-Off — Pharmacare

**Date:** 2026-08-05
**Scope:** Not a code review — an actual deployment. A real Postgres database was provisioned from nothing, migrated with the real Alembic chain, booted as a real FastAPI server, and driven end-to-end over real HTTP exactly as a pharmacy, a cashier, and two competing offline terminals would use it. The React/Tauri frontend was also launched and driven through a real login and several screens in a real browser. This is the first time in this project's review history that the actual migration chain — as opposed to `Base.metadata.create_all()`, which every automated test uses — was exercised, and it found three deployment-blocking bugs that 219 passing backend tests never could.

---

## 1. Verdict

**Go, with the migration and price-contract/refund fixes in this report now applied.** Every one of the three blocking bugs found below is fixed, verified by both the full automated suite (219 backend / 187 frontend, all passing) and by re-running the full live orchestration end-to-end afterward (60/60 orchestration assertions passing against the fixed system). The encryption-at-rest gap flagged in the [2026-08-11 offline-first review](2026-08-11-offline-first-architecture-review.md) is unchanged and still gates deployment onto uncontrolled/field hardware — nothing in this pass changes that conclusion.

---

## 2. Why this pass found what code review and unit tests couldn't

Every previous round of work on this codebase — including 219 backend tests — provisions its database via SQLAlchemy's `Base.metadata.create_all()`, which builds tables directly from the *current* ORM model definitions. It has never once executed the actual Alembic migration chain that every real deployment runs. That chain has its own, independent history — 47 migrations, several branch points and merges from parallel feature development — and nothing has ever verified that walking it from an empty database on a real Postgres server actually produces a working system. It hadn't. Three separate bugs, all invisible to model-based test provisioning, meant this application could not have been deployed fresh and used for a single sale before today.

## 3. Bugs found live, and fixed

### 3.1 [Blocker] `alembic upgrade head` failed outright on a fresh database

**Symptom:** `DROP INDEX ix_drugs_barcode: does not exist`, then (after fixing) `column "branch_id" of relation "prescriptions" already exists`, then `no such table: branch_inventory`-class failures — a cascade of three separate collisions.

**Root cause:** migration `15a1c14d1b9b` ("add branch id to prescriptions") was autogenerated on a development branch that had diverged from `7e8f9a0b1c2d` (scope_business_identifiers_by_tenant) and `fa1b2c3d4e5f` (reconcile_production_schema) — two other migrations that, on the branch that actually merged first, already performed the same index-scoping and `prescriptions.branch_id` additions. When the branches were merged, nobody caught that `15a1c14d1b9b` had become entirely redundant with work already done earlier in the true merged order. It also unconditionally dropped `idx_drug_search` (the drugs table's GIN full-text index) with nothing anywhere in the chain ever recreating it — a silent search-performance regression on every install, fresh or upgraded.

**Fix:** rewrote `15a1c14d1b9b` to be introspection-based and idempotent (check current DB state via `sa.inspect()` before each operation), matching the defensive pattern the codebase's own later "repair schema drift" migrations already established — so it's correct regardless of which parallel branch Alembic happens to apply first, not just correct for the one ordering this run happened to hit.

**Verified:** `alembic upgrade head` now completes cleanly on a brand-new database, confirmed by resetting and re-provisioning from scratch multiple times during this session.

### 3.2 [Blocker] No sale of any kind could be processed on a fresh organization

**Symptom:** the very first attempted sale in this orchestration — a plain cash walk-in sale, no insurance, no contract — failed with `404 Price contract not found or not active.`

**Root cause:** `SalesService.process_sale` unconditionally calls `load_and_validate_contract(contract_id=sale_data.price_contract_id, ...)`, and that function had no handling at all for `contract_id=None` — the WHERE clause `PriceContract.id == None` simply never matches, so it 404s. Every single existing test that exercises `process_sale` (dozens, across `test_sales_service.py`, `test_sales_contracts.py`, `test_workflows.py`) creates its own `PriceContract` first and passes it explicitly — there is no test anywhere for the plain no-contract case, because it was assumed (reasonably, given `PriceContract.is_default_contract` exists specifically for this) that a default-contract fallback existed. It didn't, and onboarding never created one either.

**Fix:** two changes, both required:
1. `load_and_validate_contract` now falls back to the organization's `is_default_contract=True` contract when none is explicitly specified, with a clear, actionable error (not a generic 404) if the org has no default contract configured.
2. `OrganizationOnboardingService` now seeds a "Standard Pricing" default contract (0% discount, all branches) for every newly onboarded organization, so a fresh org can sell immediately with zero manual setup.

**Verified:** live — a plain cash sale on a freshly onboarded org now succeeds; regression tests added (`test_sale_without_explicit_contract_falls_back_to_org_default`, `test_sale_without_contract_and_without_org_default_gives_actionable_error`).

### 3.3 [Blocker] Partial refunds were completely broken in every real deployment

**Symptom:** `409 IntegrityError` on the very first partial refund attempted in this orchestration; Postgres log showed `new row for relation "sales" violates check constraint "check_sale_status"`.

**Root cause:** the `check_sale_status` CHECK constraint, as actually created by migration `4a8c7a6b5ba3` (the initial migration), only permits `('draft', 'completed', 'cancelled', 'refunded')`. `app/models/sales/sales_model.py` — the live ORM model — has permitted `'partially_refunded'` for some time (it's what `SalesService.refund_sale` sets for any refund that isn't a full refund), but no migration was ever written to actually alter the database constraint to match. Every environment provisioned via `alembic upgrade head` — every real deployment — could accept full refunds but not partial ones, and this was completely invisible to the test suite for the same `create_all()` reason as above.

**Fix:** new migration `bc23de45fa67` corrects `check_sale_status` to include `'partially_refunded'`. While writing it, a systematic diff of every `CheckConstraint` declared across `app/models/` against every one ever created by any migration turned up two more of the same class of drift — `sale_items.check_sale_item_refunded_quantity`, `sale_items.check_sale_item_refunded_not_exceed_quantity`, and `branch_inventory.check_selling_price_nonnegative` — declared in the model, never added to the database. These are pure safety-net additions (the application code already correctly enforces the invariants; the constraints were a missing second layer of defense, not an active bug), added in the same migration for the same reason: the model is the intended source of truth, and the database should match it.

**Verified:** live — a partial refund (1 of 5 units) now succeeds; regression test added to `test_organization_onboarding.py` and a dedicated assertion in the refund flow.

## 4. A correction to my own earlier work

In an earlier cleanup pass on this project, I deleted `create_admin.py` from the repo root, judging it disposable debug clutter (hardcoded credentials, ad hoc script). It is not — it is the *only* mechanism in this codebase for creating the platform's first super-admin account, which the organization-onboarding endpoint requires as a precondition (`require_super_admin`) with no other bootstrap path. I discovered this the moment I actually tried to onboard an organization from a genuinely empty database and had no way in. It's restored. This is exactly the class of mistake live orchestration catches and a code-only review does not: I had judged the script by its appearance, not by whether anything else in the system could do its job.

## 5. What was verified live (60/60 orchestration assertions)

All of the below ran against a real uvicorn process, a real Postgres 14 database provisioned from an empty schema via the actual Alembic chain, and a real cr-sqlite-backed shadow database — not mocks, not `create_all()`.

**Setup (36/36):** organization onboarding → custom roles → staff users (including a user whose branch access is later revoked to empty, simulating the P2/I3 authorization-gap scenario from the prior review) → drug catalogue (OTC + Rx-required) → supplier → purchase order → submit → approve → receive goods **twice against the same batch number**, live-confirming the I1 duplicate-batch-append fix: `batches_created: 0` on the second receipt, one physical batch row, `remaining_quantity` correctly summed to 100.

**Sales (8/8):** cash sale with correct stock decrement; Rx-required drug correctly rejected without a prescription; correctly accepted with one, by a pharmacist-level user (a plain cashier is correctly refused — `manage_prescriptions` required, a real regulatory control, not a bug); oversell rejected; a cashier without `process_refunds` cannot call the refund endpoint at all (route-level gate, not just the named-approver check); a real manager processes a partial refund successfully.

**Sync (16/16):**
- A user cannot push sync data for a branch they aren't assigned to.
- **Concurrent oversell:** two offline-created sales, each independently believing the full remaining stock (96 units) was available, pushed together — exactly one is accepted, the other correctly rejected, stock lands at precisely zero, never negative. (Sent as two records in one push call, so this exercises the server's row-locking safety under sequential processing within a batch, not two genuinely simultaneous separate connections — the underlying `with_for_update()` locks are the same code path either way, but noted as a slightly narrower test than true parallel-connection concurrency.)
- **Price drift:** branch price changed server-side, then an offline sale citing the old price is pushed — it still syncs (drugs were already dispensed, correctly not blocked) and a `SystemAlert` fires with the exact expected message, confirmed via direct DB query, not just the API response.
- **Clock skew:** a sale dated 2 days in the future is rejected with the forward-skew guard's message.
- **Audited void:** a cashier without `process_refunds` cannot void a failed sale; a manager can, and the resulting `audit_logs` row was confirmed via direct query to contain the sale number, reason, approver, and voider.
- **Authorization gaps:** a user with zero assigned branches gets an empty prescription search, empty prescription list, and empty purchase-order list — never an org-wide leak.
- **Cross-tenant isolation:** a second, fully independent organization was onboarded live; the first organization's admin cannot read the second organization's branch inventory (403/404, not data).

**Frontend (smoke, zero console errors across every screen):** the actual Vite dev server was launched and driven with a real headless browser. Login succeeds against the real backend; the drug catalogue renders the exact two drugs created via the API; the inventory and POS screens degrade gracefully to a clean "no branch selected" / "no drugs available" empty state rather than crashing, in the parts of the app that depend on Tauri's native `invoke()` bridge and local SQLite (unavailable in a plain browser — expected, not a finding); the branch switcher correctly lists both real branches from the API. Screenshots captured for each screen.

## 6. Known limitations of this pass

- **The actual Tauri desktop shell, local SQLite, and cr-sqlite client sync engine were not exercised live.** `invoke()` requires the native webview + Rust backend, unavailable in this headless environment; the frontend was driven through a plain browser instead, which is why it correctly shows empty states rather than functioning offline. This is not new risk — the client-side sync engine (`localDb.ts`, `syncEngine.ts`) already has extensive automated coverage from the two prior review rounds (187 frontend tests, including real cr-sqlite-extension-backed migration tests) — this pass adds live server-side confidence and confirms the UI layer doesn't crash without it, but doesn't add new live proof of the local-DB code path specifically.
- **CRR (cr-sqlite CRDT) push/pull cross-tenant isolation was not re-exercised over raw HTTP in this pass.** Constructing valid `crsql_changes` payloads by hand would require building a small cr-sqlite client from scratch; the underlying isolation mechanism (`crr_row_owners`, per-table push validators) was already exhaustively verified against the real extension in the 2026-08-04 review's automated tests. This pass instead verified the equivalent real-world property — cross-org data isolation — through the regular REST API, which shares the same organization-scoping dependency chain.
- **Encryption at rest is unchanged** from the 2026-08-11 review's conclusion: local device storage is still plaintext, still gates deployment onto uncontrolled/field hardware, still requires the multi-week SQLCipher project scoped there. Nothing in this pass touches that.
